# vCard Generator Engine (vCGE): Architecture & Project Brief

**Creators:** raven575, Gemini & Claude

## 1. Core Goal & Privacy-First Design
The vCard Generator Engine (vCGE) is a high-security, cross-platform digital business card processing system designed around zero-trust, offline-first, and privacy-focused principles. Its primary goal is to ingest physical or digital business cards, extract contact text locally via WebAssembly OCR, and generate interactive 3D business cards with scannable vCard QR codes without leaking sensitive information to external cloud servers.

## 2. Modular Architecture
The application is structured into a strictly modular ES Architecture consisting of eight functional modules and a global shared library:
- **vCGE-SHARE:** Global shared utilities (event bus, data schemas, cryptography helpers, regex matchers, vCard formatters).
- **vCGE-MOD01:** Container shell, theme state, and security network interceptor.
- **vCGE-MOD02:** Temporary vault, memory only: nothing is stored; the card is held encrypted (AES-GCM-256) only while hidden behind the session PIN.
- **vCGE-MOD03:** The Capture card: Take a photo or Upload a photo, a clean viewfinder with corner brackets, a vertical zoom fader, a round green shutter, and the crop & straighten step (handles at the full edge, Rotate 90°, Snap to card) that hands the photo on with OK.
- **vCGE-MOD04:** On-device WebAssembly OCR engine powered by Tesseract.js for air-gapped text extraction.
- **vCGE-MOD05:** Contact form schema mapper, regex heuristic auto-mapper, and debounced address autocomplete suite.
- **vCGE-MOD06:** Virtual business card GUI featuring an interactive 3D card flip renderer and customized typography bindings.
- **vCGE-MOD07:** Offline vCard 3.0/4.0 syntax builder and HTML5 Canvas QR code matrix generator.
- **vCGE-MOD08:** Outbound sharing controller functioning as the sole egress gateway for Web Share payloads, .vcf downloads, PNG exports, and physical card printing.

### 3.1 What works (verified)
- **Integration:** `src/main.js` wires every module over one event bus: MOD03 camera or upload → MOD04 OCR → MOD05 mapper → MOD06 card view → MOD07 vCard and QR → MOD02 temporary vault and MOD08 egress. `index.html` is the full app UI, loaded as ES modules (`<script type="module">`).
- **One schema, one bus, one format:** `share/cardSchema.js` (`CONTACT_FIELDS`, `CONTACT_LIST_FIELDS`, schema 3.1) is the only contact schema; form element IDs, the mapper output and the vault payload all use it. `share/contactOptions.js` is the only source of the form's choices (prefixes, suffixes, unit types, phone/email/website types, countries, region lists) and the OCR mapper reads its region lists from there too. `share/eventBus.js` (`globalEventBus`, `Events`) is the only event system. `share/vcardFormatter.js` is the only vCard builder: MOD07 delegates to it, and it escapes text per RFC 2426, uses CRLF per RFC 2425, and sets the PHOTO type from the image. MOD05 `ContactFormMapper` is the only OCR text mapper. It classifies each line by context clues instead of first match wins: line labels (E, T, M, W, Tel, Cell, Fax...), email and web-address shapes that survive common OCR slips (a space for the dot, "©" for "@", no `www`), street words and PO Boxes, City/State/ZIP with the comma optional, full state names and repaired codes ("Mi", "M\\" → MI), a broad job-title vocabulary, company suffixes, and cross-checks (name vs. email username, company vs. web/email domain, with the domain used when the company is only in a logo). Taglines and logo debris are kept out of the company and street fields: a line opening like a slogan ("Your…", "Our…", "Helping…") is never the company unless it matches the web or email domain, even when it contains a company word ("Your Technology Advisor"), and "The …" names match their domain ("The Home Depot", homedepot.com). Email and web addresses survive the "I" of a domain read as "\\" or "|" ("BrightPath\\T.com" → BrightPathIT.com), and on a labelled web line one word after a bare domain is its path ("example.com Holland" → example.com/Holland, the slash read as a space). A company taken from the domain keeps the domain's capitals (BrightPathIT). The OCR's second guesses (MOD04 `alts`) settle the I/l bar: inside a web or email address, a letter the OCR also read as "I" becomes "I" when it follows a letter and comes before a capital ("TeamLogiciT.com" → TeamLogicIT.com); elsewhere the OCR's pick stands. A web path ending in a letter and a bar that together make the card's own state code ends in that code ("/Kalamazoom\\" on a Michigan card → /KalamazooMI). An email domain at most 2 letters away from the card's web address (same ending, a name of 6+ letters) is an OCR slip and takes the web address's spelling ("nzafer@TeamlLogiciT.com" with TeamLogicIT.com → nzafer@TeamLogicIT.com); a domain further away is left as read, and in the review box one that differs only in capitals takes the web address's capitals ("TeamlogicIT.com" → TeamLogicIT.com). A "/" after the web ending read as a bar before a capital is a "/" again ("TeamLogicIT.comIKalamazoo" → TeamLogicIT.com/Kalamazoo). Job-title words are repaired against the title vocabulary when exactly one title word fits: vowels read as other vowels ("Ganaral" → General) or one dropped letter ("Manger" → Manager). A ZIP code the card's state does not use (by its first three digits) is not changed, but the review box shows a note under it ("42024 is not a Michigan ZIP code"), as it does for lines with words the OCR was unsure of; editing the line clears the note. The review box shows each line as the value it will fill: the line label ("E", "T", "M", "w"...) is left out once it has set the field, and email and web addresses are shown repaired ("w BrightPath\\T.com Holland" → BrightPathIT.com/Holland); a line with several numbers keeps its labels. A phone line with one labelled number is shown in the review picker as Work / Mobile / Home / Fax phone. It works in two steps, `classifyLines` (a role per line) and `buildFields` (fields from roles); `parseOCRText` and the review screen both use them, so there is one set of rules. A card with no recognisable name line leaves the name empty rather than inventing one. Every module is an ES module.
- **MOD02 temporary vault (memory only, nothing stored):**
  - The app opens straight to an empty card. Nothing is written to browser storage: no card, no vault, no passphrase. Vaults saved by older builds (`vCGE_secure_vault.dat`) are deleted at startup, and on the desktop so is the old keychain device key they were bound to.
  - **Wipes:** everything (card, photo, review, last scan, Undo copy, held card, session PIN, biometric enrolment) is wiped when the page is left or reloaded (`pagehide`, which also covers the back/forward cache), after 7 minutes without activity while the card is open, 7 minutes after a lock (the timer restarts at the lock, raven575 2026-10-17), after 5 wrong PINs, and by hold-to-wipe (`mod02-vault/wipeDialog.js`): the red trash button on every card, the Vault page's wipe button and "Wipe and start over" on the lock screen all open one question, "Are you sure you want to wipe everything and start over?", with an unticked box "Also delete my saved settings" that asks "Are you sure?" once more before it counts; green Yes must be held 1.5 s (it fills light to dark green, a light sweeps, the vault wipes and the page reloads; letting go early cancels), red No is one tap, Esc or a sideways swipe and counts as activity. Deleting the settings is a data-free bus signal (`SETTINGS_WIPE_REQUESTED`) that Shell answers by clearing its own entry. In colour-blind mode (`html[data-cb="1"]`) Yes reads "Hold to wipe" and a fill bar shows. Without a session PIN it is also wiped after 30 s out of view (another app or tab, screen off) and after 2 minutes idle. The deadlines are checked every second and again as the page comes back, because phones freeze background timers. Out of view within 5 s of the app opening the photo picker, a download, a share action or the biometric sheet counts as that picker or sheet: neither the lock nor the 30 s applies, only the idle rule.
  - **Back guard:** after the first tap or key press the app adds one history entry (browsers skip entries added without a user gesture). Back, by button or swipe, lands on it and the app asks "Leave vCGE?": Stay keeps everything, "Wipe and leave" wipes and goes back. With an empty card Back just leaves.
  - **Session PIN (the Vault page: header padlock, Welcome's "Set Up PIN/BIO Lock Now", or Settings):** exactly 4 digits (number keypad) for this session only; set, change or remove it there (it is not offered on its own, and never saved: fresh every visit, decided 2026-10-17). With a PIN set, the screen turning off or another app coming to the front locks the card at once, and so do 2 minutes idle and the Lock button: the card and any scan in progress (the photo, the open review step with its edits, and "Reopen last scan") are held in `TemporaryVault`, encrypted with a random AES-GCM key made for that lock alone, in memory only. The card survives the screen timeout: it is wiped only by leaving the page, a wipe, 5 wrong PINs or 7 minutes after the lock. The lock screen leads with a big "Use fingerprint or face" button when biometric is on (focused, so no keyboard pops up), then the PIN box; there is no Unlock button: it unlocks as soon as the 4th digit is typed, puts everything back as it was (crop corners start over) and drops the key. The panel scrolls and the PIN box is kept in view, so a phone keyboard never covers a control. A lock whose card could not be sealed or read back says so and wipes, rather than opening an empty card. The PIN itself is never stored: only a salted PBKDF2 hash, in memory.
  - **Biometric unlock (Security → Quick unlock, once a PIN is set):** Face ID, Touch ID, fingerprint or Windows Hello, through the device's own platform authenticator (WebAuthn, `mod02-vault/biometric.js`), on the device only. Enrolling creates a credential for this site and then runs one check at once: only a check that passes turns it on, otherwise the real error name is shown and the PIN stays the only way. vCGE keeps its id and public key in memory for this session only, so each session enrols afresh, and removing the PIN or any wipe drops it. Unlocking asks the device to sign a fresh random challenge after it has checked the user, and the app verifies the signature, challenge, origin, site and user-verified flag. The PIN stays the fallback. Offered only where the device reports a platform authenticator; it needs HTTPS or localhost. The device may keep the credential in its own password manager (no contact data). Tested in Chromium with a virtual authenticator; not yet on real phones or in the desktop app's webviews.
  - **Hub store (built, not yet wired in):** `mod02-vault/vaultStore.js` is the store meant to replace direct hand-offs in `main.js`. It has one memory-only slot each for the photo, OCR text, review, contact, last scan, Undo copy and the logo (written by Export when the person ticks "Also use this logo on my card" under the QR styles, read by the card view, wiped with the rest). Values are copied in and out, change notices name the slot but carry no data, and `lock()`/`unlock(pin)`/`wipe()` cover every slot together (a seal that fails is reported as lost, not as unlocked). Each module gets a handle limited to its own slots: camera writes the photo; OCR reads the photo and writes the text; mapping reads the text and writes the review; card view reads the review and owns the contact and Undo; QR reads the contact; egress reads the contact only during a user gesture. `mod02-vault/wipePolicy.js` holds the same wipe rules as `main.js` (2 min idle lock or wipe, lock on going out of view with a PIN or wipe after 30 s without, 7-minute reset, pagehide, the 5 s picker grace) against the store, which also unlocks by biometric. Moving `main.js` and the modules onto it is a later step.
  - The header badge reads "Vault: UNLOCKED" (green) while the card is on the page and "Vault: LOCKED" while it is held behind the PIN.
  - **No save-password prompts:** where the browser can mask a plain text field (CSS `-webkit-text-security`; Chromium, Safari and WebKit), the two PIN boxes are masked text fields (`mod02-vault/secretInputs.js`), so password managers do not treat the dialogs as a login form; elsewhere they stay password fields. Both opt out of autofill, capitalisation, autocorrect and spellcheck.
  - Storage never contains contact data, encrypted or not; this is checked in the browser and in the desktop webview.
- **vCGE-SHARE `CryptoUtils`** has no default key: it requires a passphrase, derives the key with PBKDF2, and uses a fresh salt for each encryption.
- **Icons in front of card lines (MOD04 `iconDetector.js` + `iconMatcher.js`):** many cards print an icon instead of a label (phone handset, mobile phone, envelope, globe, map pin, building, house, printer, social logos). Tesseract reads such an icon as a junk word ("Q", "B&", "©", "(»)") or as a line of its own, which marks where it is; the shape there is cut out, normalised to 32×32 and described by histograms of edge orientation (HOG, 8 px and 16 px overlapping cells), which depend on the outline far more than on stroke weight or fill, and compared with templates rendered on the device from Lucide (ISC) and Simple Icons (CC0) outlines in several stroke weights plus a drawn LinkedIn "in", Facebook "f" and X, all bundled in `src/vendor/icons/templates.json` (10 KB). Label letters the OCR missed (E, T, M...) are matched as letters, so they are never taken for icons and their label is recovered. The icon is one more clue for the mapper: phone, mobile, fax and home icons act as labels; envelope and globe mark the email and web lines; pin and building the address; a social logo next to a bare handle ("@studiocraft") gives the profile link. A label written in the text, and the text's own shape, always win. The review screen shows which icon was seen on each line. Detection is best effort: if it fails, OCR carries on without icons. **Measured accuracy** (`npm run test:icons`, real pre-processing and OCR on drawn cards, two text sizes; thresholds chosen on Material and Tabler only, Font Awesome kept out of tuning): Material 93.6% of reported icons right, 84.6% of icons found; Tabler 98.1% / 91.1%; Font Awesome (held out) 97.1% / 78.6%; no icon reported on any icon-free line (with or without label letters). Known weak spots: printer icons sometimes read as addresses (harmless: the line's phone number decides), some mobile and LinkedIn icons are missed. Confirmed in the desktop app (WebKitGTK) as well.
- **Richer contact fields (schema 3.1):** name prefix and suffix (suggestion lists, any value accepted) and middle name; typed lists of phones (Mobile, Work, Home, Main, Work fax, Home fax, Pager, Other), emails (Work, Personal, Other) and websites (Work, Personal, Blog, Portfolio, Other, and LinkedIn, X/Twitter, Facebook, Instagram, GitHub, YouTube, TikTok), each with + Add and remove; social links are recognised as typed. The address has a type (Work, Home, Other), a unit type and number (Apt, Suite, Unit, Lot, Floor, Building, Room, PO Box) and a country picker that drives the region field: a picker for the United States (50 states, DC, 5 territories), Canada, Mexico and Australia, a free-text box elsewhere, with the country's own labels (State / Province / County, ZIP / Postal code / Postcode). The vCard carries all of it: `N` with middle name, prefix and suffix; `TEL`, `EMAIL` and `URL` with their types; social profiles as `X-SOCIALPROFILE` (Apple) plus a plain `URL` (Google and others); the unit joined to the street (a PO Box in its own `ADR` slot). Cards saved in the old layout (single work/mobile phone, email and website) are converted to typed rows when the vault is unlocked. OCR fills the new fields: prefixes and suffixes, middle names, labelled phone types (Home and Fax included), Work vs Personal email (by mail provider), social profile types, units, and Canadian addresses (province, postal code, country). A scanned name or address replaces the previous one as a whole.
- **MOD03/MOD04/MOD05 intake:** the Capture card offers **Take a photo** (first) and **Upload a photo** (the device's own image picker; a non-image file or one over 10 MB is turned away with a toast). The viewfinder shows the live picture with only four thin corner brackets over it, marking a 3.5 : 2 card frame that fills most of the view and turns with the phone; a vertical zoom fader on the left (the camera's own zoom where it has one, otherwise a digital zoom of the preview) eases into each change, and a round green shutter on the right sinks when pressed (Settings' left-hand mode mirrors both; both stay 48 px from the screen edge, clear of the browser's back gesture). The shot is exactly the window the viewfinder showed (cover crop and zoom), never the whole sensor frame (`mod03-camera/viewfinder.js`). **Crop & straighten, on the Capture card:** four corner handles (mouse, touch or arrow keys) start at the full edge of the photo, never pushed in; "Rotate 90°" turns sideways photos; **Snap to card** runs an on-device edge finder (`mod03-camera/cardFinder.js`: centre-against-border shade split, the patch at the centre, its convex hull, the tightest rotated rectangle) and moves the handles onto the card only when it finds one, otherwise a toast says so. The green **OK** moves the deck to the Read card, where the area inside the corners is flattened by a perspective transform (`mod03-camera/perspective.js`, capped at 2400 px) before OCR, or the photo is used as is if no corner was moved; Cancel while reading, an unreadable photo or a timeout's Cancel go back to the photo on the Capture card. A crooked test card (rotated 24°, sheared 12°) is unreadable uncropped and reads fully once cropped. **Step 2, check the text:** every OCR line is shown in an editable box with a field picker set to the mapper's guess, and a live "Will fill" summary marks worked-out values (e.g. company from the web address). Nothing reaches the form until "Fill form"; the extracted text is cleared from the page when the dialog closes, on a new photo and on idle purge. After "Fill form", **Reopen last scan** opens the review again with the lines as last edited (no new OCR), until a new photo, idle purge or lock. With a session PIN set, an idle lock holds the photo, the review and the last scan in the temporary vault (memory only) and the PIN puts them back as they were (crop corners start over); every wipe drops them (see MOD02). A sample contact, Proceed and **Clear form** each offer **Undo** in the toast for 8 s; the previous card is kept in memory only until the next such change and is dropped on idle purge, quick lock and wipe.
- **On-device OCR:** Tesseract.js 5.1.1 runs from bundled files: the worker, the LSTM WASM core (SIMD and non-SIMD builds) and the English `best_int` model, all in `src/vendor/tesseract/`. The worker loads from a same-origin URL and caching is off, so the language data never goes to IndexedDB. On a rendered test card it correctly read all 11 fields (name, title, organization, phone, email, website, street, city, state, ZIP) in about 1.5 s, with zero external requests. Photos are converted to greyscale, resized (small photos enlarged up to 3×) and contrast-stretched, with no hard black/white threshold, so Tesseract's adaptive binarisation handles shadows and glare; the engine runs in sparse-text mode (PSM 11). A photo whose mean confidence is below 55, or with fewer than 3 confidently read words (kept low so a sharp minimal card with only a name, phone and email is accepted), is rejected and the review dialog asks for a retake (on a real phone photo: sharp 65, 1 px blur 47, 1.5 px blur 32). If the engine can't start (missing library or model, a start-up error, or no start within 60 s), MOD04 raises an error instead of hanging: the UI says OCR could not start and leaves the form unchanged. No sample text is ever substituted. While the engine starts (the first scan, about 7 MB of bundled files, and the first after a wipe) the button reads "Preparing the reader…", then "Extracting…". Every wipe and idle purge shuts the engine down, so nothing from a photo stays in it; a scan running at that moment ends quietly, and the next scan starts a fresh engine (about 0.8 s more on a desktop). Reading one photo may take 60 s at most (a desktop takes about 2 s): a phone can stop the engine mid-read when memory runs low, and Tesseract.js then never answers, so past the limit the engine is restarted and a pop-up offers Try Again (the same photo, a fresh engine) or Cancel (back to the photo step). While a photo is read, a progress bar replaces the photo buttons: it waits at 0 with "Preparing the reader…" while the engine starts, then fills fast and slows down (1 - (1 - t/60 s)², 75% at 30 s) so it is full exactly at the limit, and fills up at once when reading finishes early. Its Cancel button stops the engine at once and goes back to the photo step, with Retake photo shown. Words read with confidence below 50 are passed on as `unsure`, and the review box asks for those lines to be checked. The `OCR_TEXT_EXTRACTED` event is a signal only (confidence and icon count), never the card's text. **Second guesses (`glyphChoices.js`):** the engine is asked for its other guesses for each letter (`lstm_choice_mode` 2, no measurable slowdown). A letter read twice from the same ink (the "r" inside the "m" of "Kalamazoo" read as "rm": its box lies inside its neighbour's and the neighbour's letter was one of its guesses) is dropped, and each line carries the close runner-ups (within 20 points, at least 50) as `alts: [{ at, chars }]` for the mapper. On the tester's TeamLogic card photo, whose font draws a capital I and a lowercase l as the same bar, this takes the result from TeamLogiciT / nzafer@TeamLogiciT.com / TeamLogiciT.com/Kalarmazoom to every field exactly right; no Tesseract setting alone did (30 combinations tried: both English models, page modes, scaling 0.5–3×, line-by-line re-reads).
- **Scannable QR:** MOD07 renders with the bundled qrcode-generator 1.4.4 (MIT): UTF-8, error-correction level M, whole-pixel modules and a 4-module quiet zone. jsQR decodes it back to the exact vCard, including accented names. Data too large for one QR code shows a labelled fallback. An empty card (no name, company, phone, email, website or address) shows a blank placeholder, a white square on a black square that cannot scan, and QR PNG says "Add a contact first". The QR box has rounded corners and a drop shadow from page CSS, so the saved PNG stays plain. The QR payload leaves out the photo; the .vcf keeps it.
- **MOD05 Fields card** (`mod05-form/fieldsCard.js`, `fields.css`): the form on one card; after the Read card's hand-off (or a header icon, or the Welcome card's sample link) the whole form pops in at once (a 0.32 s scale-and-fade stepped at 26 fps, with a 4 percent overshoot; a swipe does not pop, and under reduce motion the form is simply there). An **Insert Fake Contact?** list holds the sample contacts (MOD06 supplies them as data, listed by name and company) and a green **Everything's correct** button in the lower corner on the dominant-hand side (blue in colour-blind mode) moves on to the 3D Card.
- **MOD05 local address suggestions** fill in street, city, state, ZIP and country, with no network lookup.
- **MOD06 3D Card:** live preview on a card face coloured by one of eight fall palettes (Pumpkin, Maple, Harvest Gold, Cranberry, Spruce, Sage, Slate Blue, Twilight; each a card colour, an ink and an accent, ink on card at 4.5:1 or better), three typefaces (Inter, Playfair Display and Fira Code, bundled as OFL-1.1 WOFF2 in `src/vendor/fonts/`), every phone, email and website on the card with its label (past two of a kind a line is left off the printed card), and the spin: a tap flips, a sideways drag on the card turns it and it settles on the nearest face, stepped at 26 fps with a small snap, instant under reduce motion, never from within 48 px of the screen edge. Logo (PNG, JPEG, GIF, WebP or SVG, 2 MB limit; an SVG with only a viewBox gets its size from it): a white background joined to the edge is removed on the device first; a one-colour logo is then traced into a plain two-colour SVG (paths only, `currentColor`) that takes the card's ink colour; a logo of more colours (or too faint, or too detailed) is kept as a picture, trimmed, PNG with its transparency, and the toast says why. The vCard PHOTO is always the raster: a 256 px square JPEG with the trimmed logo fitted inside a margin on an opaque background (the logo's own edge colour, or for a transparent logo white, or dark slate when it is mostly light); a photo in another format is left out of the vCard. A picture logo that would vanish on the card gets a plate (accent on a light card for a light logo, ink on a dark card for a dark one); a wide logo (2:1 or wider) gets a strip across the top instead of the 64 px badge and stays in the badge on the printed card. Toasts sit at the top under the header for 3 s (8 s with an Undo button), a tap dismisses one and a hold keeps it until 3 s after the release. The typeface and palette are part of the card (`cardFont`, `themePalette`: kept by Undo and across a PIN lock); Clear and every wipe go back to Sans, Slate Blue and the front side. The sample contacts are the nine Team vCGE pilots (reserved 555-01xx numbers, example.com, each with a bundled Noto Emoji animal as its logo, Apache-2.0), listed on the Fields card. Tested at desktop width and at 390 px wide with no horizontal scroll.
- **Ephemeral memory lifecycle (120 s TTL):**
  - `TTLMemoryStreamManager` uses a wall-clock deadline, so timers throttled in background tabs cannot extend it.
  - Any pointer, key or input activity restarts it. While a card is open, a thin strip under the header shows the time left ("Locks in" with a PIN, "Clears in" without) as a slowly emptying bar; the last 20 seconds turn it amber (never red) with one quiet "Still there?" note. Nothing flashes or makes a sound. The lock screen shows a calm ring with the time left before the 7-minute reset.
  - After 120 s idle it purges RAM: it zero-fills the contact snapshot, clears the form, preview and QR, drops the captured image and review modal, and stops the camera.
  - Without a session PIN the purge wipes the card. With one, it is a quick lock that the PIN or biometric can undo (the card and the scan in progress are held encrypted in memory) until 7 minutes have passed since the lock; then they are wiped.
  - **Padlock hand-off (`mod02-vault/lockHandoff.js`):** Vault has no card. Each move between step cards (the deck's `CARD_CHANGED` signal, never from or onto Welcome) plays a small combination padlock in the middle of the screen: the shackle closes with a 5 percent overshoot, the dial turns and the glow goes orange to green, then it opens and goes back to orange, 1.4 s in all at 26 stepped frames a second. It has no words, cannot be tapped (`pointer-events: none`), announces "Details locked in the vault, moving on." once for screen readers, and under reduce motion shows the still end state for 0.7 s. The shackle position carries the state, so colour is never the only cue.
  - Each purge is logged as `RAM purged (idle)`.
  - On every start, plaintext keys and saved vaults left by older builds are deleted (startup residue check).
- **MOD08 egress:** .vcf download, share sheet (clipboard fallback), QR PNG export, email, SMS and print all go through `egressController`. SMS carries a readable summary (name, title and company, every typed phone, email and website, the address). Email shares the .vcf as an attachment where the device can share files (iPhone, iPad, Mac Safari); elsewhere (Android Chrome and desktop browsers do not share .vcf files, and a mailto: link cannot attach) the mail app opens with the summary plus the vCard text. Print / Save as PDF produces one page with the card front and back (QR) at 3.5" × 2" from a hidden print sheet (`print.css` is the only print stylesheet); the copies are rebuilt on each print and cleared on idle purge and lock, not on `afterprint`, which some browsers fire before the PDF is drawn. Each action publishes `EXPORT_DISPATCHED`, and the Security panel shows an audit log of egress, blocked requests, vault and OCR events.
- **Tauri v2 desktop app (`src-tauri/`):**
  - Vite (`vite.config.mjs`) bundles the UI into `dist/`; the vendor files are copied verbatim.
  - Tauri 2.12.0 (crate family pinned to one release set) embeds it.
  - The CSP is set in both `tauri.conf.json` and `index.html`; besides `'self'`, it allows only Tauri's local IPC (`ipc:`, `http://ipc.localhost`). The gatekeeper allows the same two.
  - The one app command (`delete_device_secret`) is gated by a capability: only the `main` window may call it, and no other Tauri API is exposed.
  - Verified on Linux, both debug and release (9.7 MB binary, 7 MB `.deb`): the bundled UI loads, real OCR runs in WebKitGTK, QR decodes, external fetch is blocked, and webview storage holds no contact data.
- **OS keychain clean-up:** builds before the memory-only vault bound the saved vault to a random device key in the OS credential store (`keyring` crate: macOS Keychain, Windows Credential Manager, Linux Secret Service). Nothing is stored there now. When the app finds an old keychain-bound vault at startup it deletes it and calls `delete_device_secret`; no command can create a key any more (checked in the desktop test against a real Secret Service).
- **No network egress:**
  - The MOD01 network lock (`netLock.js`) is a classic script at the top of `index.html`, so it runs before the bundled libraries and every module. It wraps `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource` and `sendBeacon` and blocks every non-same-origin request; `shell.js` publishes each block as `EGRESS_BLOCKED` with the scheme and host only.
  - The OCR worker starts through `workerGuard.js`, which applies the same rule to the worker's `fetch`, `XMLHttpRequest`, `importScripts` and `WebSocket` (the page's interceptor and CSP meta tag do not reach a worker) before loading Tesseract's worker.
  - **Browser gate (`browserGate.js`, ES5, loaded right after `netLock.js`):** feature checks only; nothing is sent, stored or fetched. If a protection vCGE relies on is missing (ES modules, an enforced CSP, a secure context, Web Crypto, WebAssembly, Workers, or `netLock.js` itself), the app never starts and the bundled "This app cannot run in this browser" page (`mod01-shell/unsupported/`) lists what is missing and links to alternatives, free and open source browsers first (Firefox, Firefox ESR for Windows 7/8/8.1, Brave), then Edge, Chrome and Safari; links are plain user-clicked navigations with `rel="noopener noreferrer"` and no query data. A script the engine cannot parse while the page loads opens the same page instead of leaving it blank. If only something outside the app is weak (Windows 7/8/8.1, Chromium 109 or older, no camera, no 3D flip), the app runs with a dismissible banner. Decision: raven575, 2026-10-15.
  - **Welcome pop-up and tour (`welcome.js`, opened by `shell.js`):** every time vCGE starts, a pop-up offers START NOW or "Show me around", a six-step tour that spotlights the scan panel, the form, the 3D card, Share & export, the Security panel and the header. Nothing records that it was seen (no storage, cookie or flag), so it shows on every new session; it is not shown again after a lock or wipe. The rest of the page is inert while it is open; Esc or the backdrop closes it. It reads and sends no contact data. No sound, no flashing; a short fade, off under reduced motion. Decision: raven575, 2026-10-16.
  - The event bus carries signals only: `IMAGE_CAPTURED` and `OCR_TEXT_EXTRACTED` hold no photo or text, and the bus is not exposed on `window`.
  - The CSP restricts scripts, styles and connections to `'self'`.
  - Tailwind is compiled locally (`npm run build:css`).
  - A full browser session made zero non-local requests, and same-origin requests still work.

### 3.2 Remaining gaps
1. **macOS and Windows are built but not run:** builds and Rust tests pass in CI on both (installers produced), but the apps have not been launched or tested end to end there, so the window, OCR and keychain clean-up are unverified on those systems. Code signing and notarisation are not set up.
2. **Zero-fill is best-effort by nature:** the purge removes every reference the app holds and overwrites what it can, but JavaScript strings are immutable and garbage-collected, so the engine may keep copies in freed memory until they are reclaimed. Contact data lives in the webview (JavaScript), so native memory wiping would not cover it either.
3. **Camera capture in the desktop webview is untested:** the container has no camera. WebKitGTK needs camera permission handling, which may need work on real hardware.

## 4. Key Technical Decisions
- **RAM TTL Streams:** To eliminate persistent data residue risks, visual renderers and QR generators consume short-lived, read-only memory streams protected by a 120-second TTL auto-purge protocol and startup memory residue checks. *(Status: wired in — 120 s idle purge plus a startup residue check; see 3.1, with the zero-fill limits in 3.2 #2.)*
- **Sole Egress Gateway:** Sub-modules are strictly blocked from making direct network calls; all external sharing routes exclusively through MOD08 to enforce total telemetry visibility. *(Status: enforced — the MOD01 gatekeeper blocks non-same-origin network calls and the CSP restricts connections to `'self'`; see 3.1.)*
- **Dual-Licensing Model:** The public repository utilizes an MIT License for open-source transparency and auditability, while preserving the legal right to distribute pre-compiled binary packages under a proprietary commercial EULA. *(Status: every bundled dependency is MIT or Apache-2.0; GPL-3.0 QRious was replaced with MIT qrcode-generator to keep the commercial option open. See `THIRD_PARTY_NOTICES.md`.)*
