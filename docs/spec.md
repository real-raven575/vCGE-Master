# vCard Generator Engine (vCGE): Architecture & Project Brief

**Creators:** raven575, Gemini & Claude

## 1. Core Goal & Privacy-First Design
The vCard Generator Engine (vCGE) is a high-security, cross-platform digital business card processing system designed around zero-trust, offline-first, and privacy-focused principles. Its primary goal is to ingest physical or digital business cards, extract contact text locally via WebAssembly OCR, and generate interactive 3D business cards with scannable vCard QR codes without leaking sensitive information to external cloud servers.

## 2. Modular Architecture
The application is structured into a strictly modular ES Architecture consisting of eight functional modules and a global shared library:
- **vCGE-SHARE:** Global shared utilities (event bus, data schemas, cryptography helpers, regex matchers, vCard formatters).
- **vCGE-MOD01:** Container shell, theme state, and security network interceptor.
- **vCGE-MOD02:** Secure storage vault utilizing AES-GCM-256 encryption at rest and native OS keychain integration.
- **vCGE-MOD03:** Active camera and acquisition viewfinder with zoom controls and a post-capture crop/warp preview modal.
- **vCGE-MOD04:** On-device WebAssembly OCR engine powered by Tesseract.js for air-gapped text extraction.
- **vCGE-MOD05:** Contact form schema mapper, regex heuristic auto-mapper, and debounced address autocomplete suite.
- **vCGE-MOD06:** Virtual business card GUI featuring an interactive 3D card flip renderer and customized typography bindings.
- **vCGE-MOD07:** Offline vCard 3.0/4.0 syntax builder and HTML5 Canvas QR code matrix generator.
- **vCGE-MOD08:** Outbound sharing controller functioning as the sole egress gateway for Web Share payloads, .vcf downloads, PNG exports, and physical card printing.

### 3.1 What works (verified)
- **Integration:** `src/main.js` wires every module over one event bus: MOD03 camera or upload → MOD04 OCR → MOD05 mapper → MOD06 card view → MOD07 vCard and QR → MOD02 vault and MOD08 egress. `index.html` is the full app UI, loaded as ES modules (`<script type="module">`).
- **One schema, one bus, one format:** `share/cardSchema.js` (`CONTACT_FIELDS`, `CONTACT_LIST_FIELDS`, schema 3.1) is the only contact schema; form element IDs, the mapper output and the vault payload all use it. `share/contactOptions.js` is the only source of the form's choices (prefixes, suffixes, unit types, phone/email/website types, countries, region lists) and the OCR mapper reads its region lists from there too. `share/eventBus.js` (`globalEventBus`, `Events`) is the only event system. `share/vcardFormatter.js` is the only vCard builder: MOD07 delegates to it, and it escapes text per RFC 2426, uses CRLF per RFC 2425, and sets the PHOTO type from the image. MOD05 `ContactFormMapper` is the only OCR text mapper. It classifies each line by context clues instead of first match wins: line labels (E, T, M, W, Tel, Cell, Fax...), email and web-address shapes that survive common OCR slips (a space for the dot, "©" for "@", no `www`), street words and PO Boxes, City/State/ZIP with the comma optional, full state names and repaired codes ("Mi", "M\\" → MI), a broad job-title vocabulary, company suffixes, and cross-checks (name vs. email username, company vs. web/email domain, with the domain used when the company is only in a logo). Taglines and logo debris are kept out of the company and street fields: a line opening like a slogan ("Your…", "Our…", "Helping…") is never the company unless it matches the web or email domain, even when it contains a company word ("Your Technology Advisor"), and "The …" names match their domain ("The Home Depot", homedepot.com). Email and web addresses survive the "I" of a domain read as "\\" or "|" ("BrightPath\\T.com" → BrightPathIT.com), and on a labelled web line one word after a bare domain is its path ("example.com Holland" → example.com/Holland, the slash read as a space). A company taken from the domain keeps the domain's capitals (BrightPathIT). The review box shows each line as the value it will fill: the line label ("E", "T", "M", "w"...) is left out once it has set the field, and email and web addresses are shown repaired ("w BrightPath\\T.com Holland" → BrightPathIT.com/Holland); a line with several numbers keeps its labels. A phone line with one labelled number is shown in the review picker as Work / Mobile / Home / Fax phone. It works in two steps, `classifyLines` (a role per line) and `buildFields` (fields from roles); `parseOCRText` and the review screen both use them, so there is one set of rules. A card with no recognisable name line leaves the name empty rather than inventing one. Every module is an ES module.
- **MOD02 vault (encrypted persistence):**
  - On first run the user creates a passphrase (8+ characters) or chooses "Continue without saving". Edits are then saved with AES-GCM-256 (PBKDF2-SHA256, 100k iterations, stored salt) after a 400 ms debounce.
  - After a reload, the right passphrase restores the card and a wrong one is rejected.
  - **Vault format 2 (unlock slots):** the card is encrypted with a random 256-bit data key, and the data key is stored wrapped (AES-GCM) once per unlock method: always the passphrase, plus one slot per enrolled passkey. A wrong passphrase is detected when its slot will not unwrap. Format-1 vaults (card encrypted with the passphrase key itself) open as before and are converted on their first unlock; tests cover browser and keychain-bound format-1 vaults. The data key is held as a non-extractable key while unlocked.
  - **Quick unlock (so the passphrase is not retyped all day):**
    - *Session PIN:* after each full unlock the app offers a PIN or short password (4+ characters) for this session only (also under Security → Quick unlock: set, change, remove). Once a passkey is enrolled the offer is not shown on its own, since the passkey is already the quick way back in; the Security panel still sets a PIN. After the 2-minute idle timeout the card is cleared from the page but the data key stays in memory for 5 minutes, and the PIN brings the card back, together with a scan in progress (the photo, the open review step with its edits, and "Reopen last scan"), which is kept in memory only, encrypted with the data key, while locked. When the 5 minutes end, after 5 wrong PINs, on Lock, on reload or on "Continue without saving", the key and the PIN are both dropped and the passphrase (or a passkey) is needed. The PIN itself is never stored: only a salted PBKDF2 hash, in memory.
    - *Passkeys (WebAuthn PRF):* Security → Quick unlock → "Add a passkey" (confirmed with the passphrase) enrolls the device's own verification: Face ID or Touch ID, Windows Hello (face, fingerprint or PIN), Android fingerprint or face unlock, or a security key. The PRF extension returns 32 secret bytes only after the device verifies the user; HKDF turns them into the key that wraps the data key (mixed with the OS keychain device key on keychain-bound vaults). It works after restarts and from a quick lock, needs no server and sends nothing anywhere. Passkeys are tied to the page's address and need https or localhost. A provider without PRF is refused with an explanation, since it cannot unlock encrypted data; the passphrase always remains as the fallback.
  - Lock (the button) drops the key and the session PIN but keeps the vault. Wipe deletes it.
  - The header badge reads "Vault: UNLOCKED" (green) while the vault key is in use and "Vault: LOCKED" otherwise (locked, quick-locked, or memory-only mode).
  - **No save-password prompts:** where the browser can mask a plain text field (CSS `-webkit-text-security`; Chromium, Safari and WebKit), the passphrase, confirm, session PIN and passkey-confirmation boxes are masked text fields (`mod02-vault/secretInputs.js`), so password managers do not treat the dialogs as a login form; elsewhere they stay password fields. All of them opt out of autofill, capitalisation, autocorrect and spellcheck.
  - Storage never contains plaintext contact data; this was checked in the browser.
- **vCGE-SHARE `CryptoUtils`** has no default key: it requires a passphrase, derives the key with PBKDF2, and uses a fresh salt for each encryption.
- **Icons in front of card lines (MOD04 `iconDetector.js` + `iconMatcher.js`):** many cards print an icon instead of a label (phone handset, mobile phone, envelope, globe, map pin, building, house, printer, social logos). Tesseract reads such an icon as a junk word ("Q", "B&", "©", "(»)") or as a line of its own, which marks where it is; the shape there is cut out, normalised to 32×32 and described by histograms of edge orientation (HOG, 8 px and 16 px overlapping cells), which depend on the outline far more than on stroke weight or fill, and compared with templates rendered on the device from Lucide (ISC) and Simple Icons (CC0) outlines in several stroke weights plus a drawn LinkedIn "in", Facebook "f" and X, all bundled in `src/vendor/icons/templates.json` (10 KB). Label letters the OCR missed (E, T, M...) are matched as letters, so they are never taken for icons and their label is recovered. The icon is one more clue for the mapper: phone, mobile, fax and home icons act as labels; envelope and globe mark the email and web lines; pin and building the address; a social logo next to a bare handle ("@studiocraft") gives the profile link. A label written in the text, and the text's own shape, always win. The review screen shows which icon was seen on each line. Detection is best effort: if it fails, OCR carries on without icons. **Measured accuracy** (`npm run test:icons`, real pre-processing and OCR on drawn cards, two text sizes; thresholds chosen on Material and Tabler only, Font Awesome kept out of tuning): Material 93.6% of reported icons right, 84.6% of icons found; Tabler 98.1% / 91.1%; Font Awesome (held out) 97.1% / 78.6%; no icon reported on any icon-free line (with or without label letters). Known weak spots: printer icons sometimes read as addresses (harmless: the line's phone number decides), some mobile and LinkedIn icons are missed. Confirmed in the desktop app (WebKitGTK) as well.
- **Richer contact fields (schema 3.1):** name prefix and suffix (suggestion lists, any value accepted) and middle name; typed lists of phones (Mobile, Work, Home, Main, Work fax, Home fax, Pager, Other), emails (Work, Personal, Other) and websites (Work, Personal, Blog, Portfolio, Other, and LinkedIn, X/Twitter, Facebook, Instagram, GitHub, YouTube, TikTok), each with + Add and remove; social links are recognised as typed. The address has a type (Work, Home, Other), a unit type and number (Apt, Suite, Unit, Lot, Floor, Building, Room, PO Box) and a country picker that drives the region field: a picker for the United States (50 states, DC, 5 territories), Canada, Mexico and Australia, a free-text box elsewhere, with the country's own labels (State / Province / County, ZIP / Postal code / Postcode). The vCard carries all of it: `N` with middle name, prefix and suffix; `TEL`, `EMAIL` and `URL` with their types; social profiles as `X-SOCIALPROFILE` (Apple) plus a plain `URL` (Google and others); the unit joined to the street (a PO Box in its own `ADR` slot). Cards saved in the old layout (single work/mobile phone, email and website) are converted to typed rows when the vault is unlocked. OCR fills the new fields: prefixes and suffixes, middle names, labelled phone types (Home and Fax included), Work vs Personal email (by mail provider), social profile types, units, and Canadian addresses (province, postal code, country). A scanned name or address replaces the previous one as a whole.
- **MOD03/MOD04/MOD05 intake:** image upload (10 MB limit) and the camera viewfinder (zoom, tap-to-focus, switch, capture) open a two-step review dialog. **Step 1, crop & straighten:** four corner handles (mouse, touch or arrow keys) mark the card, and "Rotate 90°" turns sideways photos; on "Extract fields" the area inside the corners is flattened by a perspective transform (`mod03-camera/perspective.js`, capped at 2400 px) before OCR, or the photo is used as is if no corner was moved. A crooked test card (rotated 24°, sheared 12°) is unreadable uncropped and reads fully once cropped. **Step 2, check the text:** every OCR line is shown in an editable box with a field picker set to the mapper's guess, and a live "Will fill" summary marks worked-out values (e.g. company from the web address). Nothing reaches the form until "Fill form"; the extracted text is cleared from the page when the dialog closes, on a new photo and on idle purge. After "Fill form", **Reopen last scan** opens the review again with the lines as last edited (no new OCR), until a new photo, idle purge or lock. With a session PIN set, an idle purge keeps the photo, the review and the last scan sealed with the vault's data key (memory only) and the PIN puts them back as they were (crop corners start over); they are dropped with the key on a full lock, at the end of the 5-minute PIN window, after 5 wrong PINs, on "Continue without saving", on wipe and on reload. A sample preset, "Fill form" and **Clear form** each offer **Undo** in the toast for 8 s; the previous card is kept in memory only until the next such change and is dropped on idle purge, lock and wipe.
- **On-device OCR:** Tesseract.js 5.1.1 runs from bundled files: the worker, the LSTM WASM core (SIMD and non-SIMD builds) and the English `best_int` model, all in `src/vendor/tesseract/`. The worker loads from a same-origin URL and caching is off, so the language data never goes to IndexedDB. On a rendered test card it correctly read all 11 fields (name, title, organization, phone, email, website, street, city, state, ZIP) in about 1.5 s, with zero external requests. Photos are converted to greyscale, resized (small photos enlarged up to 3×) and contrast-stretched, with no hard black/white threshold, so Tesseract's adaptive binarisation handles shadows and glare; the engine runs in sparse-text mode (PSM 11). A photo whose mean confidence is below 55, or with fewer than 3 confidently read words (kept low so a sharp minimal card with only a name, phone and email is accepted), is rejected and the review dialog asks for a retake (on a real phone photo: sharp 65, 1 px blur 47, 1.5 px blur 32). If the engine can't start (missing library or model, a start-up error, or no start within 60 s), MOD04 raises an error instead of hanging: the UI says OCR could not start and leaves the form unchanged. No sample text is ever substituted.
- **Scannable QR:** MOD07 renders with the bundled qrcode-generator 1.4.4 (MIT): UTF-8, error-correction level M, whole-pixel modules and a 4-module quiet zone. jsQR decodes it back to the exact vCard, including accented names. Data too large for one QR code shows a labelled fallback. The QR payload leaves out the photo; the .vcf keeps it.
- **MOD05 local address suggestions** fill in street, city, state, ZIP and country, with no network lookup.
- **MOD06 card view:** live preview, 3D flip, five palettes, three typefaces (Inter, Playfair Display and Fira Code, bundled as OFL-1.1 WOFF2 in `src/vendor/fonts/`), avatar (PNG/JPEG, 2 MB limit), three sample presets, toasts, and app-wide light/dark mode. Tested at desktop width and at 390 px wide with no horizontal scroll.
- **Ephemeral memory lifecycle (120 s TTL):**
  - `TTLMemoryStreamManager` uses a wall-clock deadline, so timers throttled in background tabs cannot extend it.
  - Any pointer, key or input activity restarts it, and a countdown in the Security panel shows the time left.
  - After 120 s idle it purges RAM: it zero-fills the contact snapshot, clears the form, preview and QR, drops the captured image and review modal, and stops the camera.
  - In vault mode the purge also locks the vault (the encrypted copy stays on disk): fully, or, with a session PIN set, as a quick lock that the PIN can undo for 5 minutes (the scan in progress is kept encrypted for that window and comes back with the card). In memory-only mode the card is cleared.
  - Each purge is logged as `RAM purged (idle)`.
  - On every start, plaintext keys left by older builds are deleted (startup residue check).
- **MOD08 egress:** .vcf download, share sheet (clipboard fallback), QR PNG export, email, SMS and print all go through `egressController`. SMS carries a readable summary (name, title and company, every typed phone, email and website, the address). Email shares the .vcf as an attachment where the device can share files (iPhone, iPad, Mac Safari); elsewhere (Android Chrome and desktop browsers do not share .vcf files, and a mailto: link cannot attach) the mail app opens with the summary plus the vCard text. Print / Save as PDF produces one page with the card front and back (QR) at 3.5" × 2" from a hidden print sheet (`print.css` is the only print stylesheet); the copies are rebuilt on each print and cleared on idle purge and lock, not on `afterprint`, which some browsers fire before the PDF is drawn. Each action publishes `EXPORT_DISPATCHED`, and the Security panel shows an audit log of egress, blocked requests, vault and OCR events.
- **Tauri v2 desktop app (`src-tauri/`):**
  - Vite (`vite.config.mjs`) bundles the UI into `dist/`; the vendor files are copied verbatim.
  - Tauri 2.12.0 (crate family pinned to one release set) embeds it.
  - The CSP is set in both `tauri.conf.json` and `index.html`; besides `'self'`, it allows only Tauri's local IPC (`ipc:`, `http://ipc.localhost`). The gatekeeper allows the same two.
  - The two app commands are gated by a capability: only the `main` window may call them, and no other Tauri API is exposed.
  - Verified on Linux, both debug and release (9.7 MB binary, 7 MB `.deb`): the bundled UI loads, real OCR runs in WebKitGTK, QR decodes, external fetch is blocked, and webview storage holds no plaintext.
- **OS keychain binding:**
  - On the desktop, creating a vault stores a random 256-bit device key in the OS credential store. The `keyring` crate covers the macOS Keychain, Windows Credential Manager/DPAPI and the Linux Secret Service.
  - The passphrase's AES-GCM-256 key (which wraps the data key) is HKDF-SHA256(PBKDF2-SHA256(passphrase), salt = device key), and the vault records this as `kdf: pbkdf2-sha256+hkdf-device-key`. Passkey slots on such a vault mix in the device key the same way.
  - A copied vault therefore cannot be opened elsewhere with the passphrase alone. Unlocking never creates a key: a missing key is reported, and the test confirms it isn't silently replaced.
  - Wipe deletes the device key.
  - If the keychain is unavailable at creation, the vault falls back to passphrase-only and the user is told.
  - Browser vaults are unchanged and still open (a backward-compatibility test covers this).
  - Verified against a real Secret Service (gnome-keyring).
- **No network egress:**
  - The MOD01 gatekeeper is imported first. It wraps `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource` and `sendBeacon`, blocks every non-same-origin request and publishes `EGRESS_BLOCKED`.
  - The CSP restricts scripts, styles and connections to `'self'`.
  - Tailwind is compiled locally (`npm run build:css`).
  - A full browser session made zero non-local requests, and same-origin requests still work.

### 3.2 Remaining gaps
1. **macOS and Windows are built but not run:** builds and Rust tests pass in CI on both (installers produced), but the apps have not been launched or tested end to end there, so the native keychain, window and OCR are unverified on those systems. Code signing and notarisation are not set up.
2. **Zero-fill is best-effort by nature:** the purge removes every reference the app holds and overwrites what it can, but JavaScript strings are immutable and garbage-collected, so the engine may keep copies in freed memory until they are reclaimed. Contact data lives in the webview (JavaScript), so native memory wiping would not cover it either.
3. **Passkeys are tested only with a virtual authenticator:** Chromium's virtual authenticator (with and without PRF) covers enrolment, unlock, quick lock, reload and refusal, but no real phone, Mac or Windows Hello has been tried. Platform support for PRF varies: iCloud Keychain (Safari 18+, iOS 18+/macOS 15+), Google Password Manager on Android and most security keys are reported to support it; reports on Windows Hello conflict. The Linux desktop app's webview (WebKitGTK) has no WebAuthn, so the desktop app offers the session PIN only (the passkey option is hidden); WebView2 (Windows) and WKWebView (macOS) are unverified. Native desktop biometrics (Touch ID / Windows Hello through OS APIs) would need Rust code; see section 5.
4. **Camera capture in the desktop webview is untested:** the container has no camera. WebKitGTK needs camera permission handling, which may need work on real hardware.

## 4. Key Technical Decisions
- **RAM TTL Streams:** To eliminate persistent data residue risks, visual renderers and QR generators consume short-lived, read-only memory streams protected by a 120-second TTL auto-purge protocol and startup memory residue checks. *(Status: wired in — 120 s idle purge plus a startup residue check; see 3.1, with the zero-fill limits in 3.2 #2.)*
- **Sole Egress Gateway:** Sub-modules are strictly blocked from making direct network calls; all external sharing routes exclusively through MOD08 to enforce total telemetry visibility. *(Status: enforced — the MOD01 gatekeeper blocks non-same-origin network calls and the CSP restricts connections to `'self'`; see 3.1.)*
- **Dual-Licensing Model:** The public repository utilizes an MIT License for open-source transparency and auditability, while preserving the legal right to distribute pre-compiled binary packages under a proprietary commercial EULA. *(Status: every bundled dependency is MIT or Apache-2.0; GPL-3.0 QRious was replaced with MIT qrcode-generator to keep the commercial option open. See `THIRD_PARTY_NOTICES.md`.)*

## 5. Future Revisions
- **Native desktop biometrics:** where the desktop webview has no WebAuthn (Linux WebKitGTK, possibly macOS), unlock the vault through the OS instead: the macOS Keychain with a Touch ID access control, Windows Hello through `UserConsentVerifier` / the credential store, and fprintd or polkit on Linux. Needs Rust code per OS and testing on real hardware.
- **Trained icon recognizer:** if template matching (section 3.1, icons) falls short on real cards, replace or back it with a small neural-network classifier trained on many icon styles. It would generalise better to unusual designs, at the cost of a 1–5 MB model plus an on-device inference runtime and a training pipeline (with the same held-out evaluation as `tests/icons.e2e.test.cjs`). Requested to be kept in mind for future revisions (2026-10-13).
